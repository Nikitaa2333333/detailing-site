# Сайт детейлинг-центра

Многостраничный статический сайт по ТЗ [ТЗ_с_комментариями_Артур_для_Никиты_.docx](ТЗ_с_комментариями_Артур_для_Никиты_.docx).
Стек: Astro 7, чистая статика, Onest Variable, без бэкенда и без CMS.

Код проекта — в папке [akb-bu/](akb-bu/) (имя осталось от прошлого проекта, не переименовываем).

**Бизнес-задача.** Трафик из поиска и рекламы приходит сразу на страницу услуги →
посетитель выбирает марку и модель → видит цену для своего класса авто → оставляет
телефон. Всё остальное на странице работает на этот переход.

**Объём:** главная + 7 категорий + 39 страниц услуг + 13 информационных + статьи +
3 юридические + 404 и «спасибо». Все страницы — из шаблонов, различаются только данными.

## Источник правды — данные, не вёрстка

| Файл | Что в нём | Кто пишет |
|---|---|---|
| [akb-bu/src/data/prices.json](akb-bu/src/data/prices.json) | 27 разделов прайса, 162 услуги, цены по 5 классам, классификация авто (бренд → модели → класс), сноски | генерируется скриптом |
| [akb-bu/src/data/content.json](akb-bu/src/data/content.json) | тексты сквозных блоков, цифры о компании, контакты | руками |
| `akb-bu/src/data/services.json` | карта ТЗ: 7 категорий → 39 услуг → URL, title/description, привязка к разделам прайса | руками, **ещё не создан** |
| [akb-bu/src/data/service-texts.json](akb-bu/src/data/service-texts.json) | клиентские тексты услуг поверх прайса: название, суть, «что входит», условия | мы (редактура), заказчик вычитывает |
| [akb-bu/src/data/car-aliases.json](akb-bu/src/data/car-aliases.json) | как люди пишут марки и модели (Камри, крузак), кузовные коды (F20, W164), исправленные названия | мы |
| [akb-bu/src/data/car-extra.json](akb-bu/src/data/car-extra.json) | машины, которых нет в прайсе (китайцы, новые поколения: Haval, Tank, LC 300, GLC…) — класс берётся у похожей модели прайса (`like`) | мы, заказчик вычитывает аналоги |
| [akb-bu/src/data/service-intents.json](akb-bu/src/data/service-intents.json) | словарь «беда → услуги»: 30 ситуаций («поцарапали дверь», «воняет в салоне»), фразы, пояснение, подборка услуг по ключам прайса | мы, заказчик вычитывает пояснения |

**`prices.json` — файл заказчика, руками не правится никогда:** его перезаписывает импортёр.
Всё наше (тексты, вариации написания) лежит отдельными файлами по `id` раздела и услуги
и накладывается на сборке. Если заказчик переименовал или убрал услугу или модель, сборка
падает и называет осиротевший ключ — перенести запись на новый `id`.

Прайс **обновляется** — это штатный сценарий, не разовый импорт:

```bash
cd akb-bu && python scripts/import-prices.py   # xlsx в родительской папке находит сам
```

Правила:

1. Цены и классы авто в вёрстку руками не вписываются никогда — только из `prices.json`.
2. Привязка «страница услуги → раздел прайса» живёт в `services.json` по стабильному `id`
   раздела, не по порядковому номеру листа: листы в xlsx двигаются.
3. **В xlsx есть строки «Информация не для сайта! Для менеджера» и разбивка заказ-наряда
   (себестоимость работ и материалов) — на сайт попадать не должны.** Импортёр их выкидывает;
   после каждого обновления прайса это проверяется (см. «Инфраструктура»).
4. Расхождения ТЗ и прайса (нет «Дооснащения» и «Малярных работ», у «Двигателя» и «Ходовой»
   цена только для 1-го класса, у 21 услуги пошива нет клиентского описания) закрываются
   текстом «Стоимость рассчитывается индивидуально», а не выдуманными цифрами.

## Калькулятор — как он работает

Главный инструмент сайта: посетитель за минуту получает цену для своей машины и оставляет
телефон. Компонент — [akb-bu/src/components/Calculator.astro](akb-bu/src/components/Calculator.astro),
на главной стоит сразу под первым экраном (секция `#calc`, тёмная полоса).

### Сценарий посетителя

1. **Вход.** Три двери: поле «Марка или модель» на первом экране (кнопка «Рассчитать» — фокус
   в шаг 1 калькулятора), плашки услуг на главной (ведут прямо в свой раздел, шаг 3),
   прокрутка до секции.
2. **Машина.** Человек набирает как привык — «камри», «крузак», «бмв х5», в неправильной
   раскладке — список предлагает модели с классом. Выбрал — все цены пересчитываются под
   класс (1–5). Можно «Без машины — посмотреть цены «от»». Не нашлась машина — запрос
   запоминается и уходит в заявку (`searched.car`), менеджер увидит, что за авто.
3. **Направление.** Шесть плиток (от прайса, не от ТЗ) с числом услуг и ценой «от» уже для
   выбранного класса. Отмечать можно в нескольких направлениях — всё идёт в один расчёт.
4. **Услуги.** Разделы направления чипами, на экране один короткий список; карточка услуги
   целиком — чекбокс, внутри «Что входит» и условия. Поиск справа сверху работает по всем
   направлениям сразу (см. ниже).
5. **Заявка.** Слева расчёт (что выбрано, цены, итог, «цены «от» уточним после осмотра»),
   справа форма: имя, телефон с маской +7, согласие. В заявку уходят: машина и класс,
   услуги с ценами, итог, что искали и не нашли (машина / услуга), URL страницы, UTM
   (держатся всю сессию с первого захода).

Внизу карточки прилипает полоса итога: машина, сколько выбрано, сумма, кнопка следующего
шага. Выбор машины и услуг помнится в браузере (`localStorage`, ключ `ds-calc-v1`) —
вернулся на сайт, расчёт на месте.

### Поиск: три слоя, без живого ИИ

| Слой | Что ищет | Где живёт |
|---|---|---|
| Машины | марка/модель: вариации, коды кузовов, раскладка, кириллица в кодах | [lib/car-search.js](akb-bu/src/lib/car-search.js) + [lib/cars.js](akb-bu/src/lib/cars.js) + `car-aliases.json` + `car-extra.json` |
| Услуги по тексту | название, описание, раздел карточки; слово по основе («пленкой» → «плёнка») | [lib/service-search.js](akb-bu/src/lib/service-search.js) |
| Ситуации «беда → услуги» | «поцарапали дверь» → полировка; «продаю машину» → комплекс, химчистка, полировка, мойка ДВС | [lib/service-intents.js](akb-bu/src/lib/service-intents.js) + `service-intents.json` |

Как показывается ситуация: название ситуации встаёт заголовком шага, пояснение — лидом, ниже
подборка услуг с ценами класса (плюс обычные совпадения по тексту). Два совпадения — вторая
ситуация своим подзаголовком. Подсказка появляется с трёх букв недописанного слова.

**Живой ИИ в поиск не ставим** (решено 23.09.2026): сайт статичный — нужен был бы сервер,
ответ 1–3 с вместо мгновенного, риск выдуманных услуг и цен. ИИ работает один раз при
подготовке словаря — генерирует формулировки, мы и заказчик вычитываем. Вернуться к нему —
только запасным вариантом, когда словарь не нашёл, и по данным промахов (`searched.service`
в заявках покажет, что реально вбивают).

### Машины вне прайса

Прайс заказчика — 42 марки и ~370 моделей примерно 2010–2015 годов, без единой китайской
марки. Чтобы человек с Haval или LC 300 не упирался в «модели нет», такие машины лежат в
`car-extra.json` (решено 24.09.2026). Класс там не пишется: у каждой указана похожая
размером и сегментом модель из прайса (`like`), класс берётся у неё — сменит заказчик класс
аналога, сменится и тут. В списке такая модель выглядит как обычная, в заявку уходит
`car.like` — менеджер видит, что класс по аналогии. При равной оценке модель из прайса в
выдаче выше. Не нашли и тут — одна строка «„…“ нет в списке — покажем цены „от“, класс
уточнит менеджер», запрос уходит в заявку.

### Предохранители

- Словари (`car-aliases.json`, `car-extra.json`, `service-texts.json`, `service-intents.json`)
  ссылаются на прайс по `id`. Прайс переименовал или убрал модель/услугу (или аналог) —
  **сборка падает** и называет ключ. Модель из `car-extra.json` появилась в прайсе — тоже падает.
- **Автотест поиска** [scripts/test-search.mjs](akb-bu/scripts/test-search.mjs) идёт перед
  каждой сборкой (`npm run build`) и отдельно (`npm run test:search`): машины, услуги,
  ситуации — ~144 проверки «запрос → что должно найтись первым». Упал — на сайт не едет.
  Нашли промах поиска — сначала строка в тест, потом правка словаря.
- В браузер уходит только словарь ситуаций; прайс целиком в скрипт страницы не попадает
  (проверка ключей — `checkIntents()` на сборке).

### Словарь для чтения

`npm run variants` (в `akb-bu/`) собирает [ВАРИАНТЫ_ПОИСКА.html](ВАРИАНТЫ_ПОИСКА.html) —
все варианты ввода: марки и модели с классами, ситуации с фразами, все услуги и в какие
подборки они входят, с фильтром. Собирается из тех же модулей, что сайт, руками не править.
Опубликована копия: https://claude.ai/artifact/H47naEsS8QhboaGGgw6QNS (перевыкладывать после
пересборки).

### Оформление

- Цвета калькулятора — локальные токены `--wiz-*` в начале стилей компонента: светлая схема
  по умолчанию, в тёмной секции (`<Section dark>`, класс `.on-dark`) переключается сам.
  Вернуть светлый — убрать `dark` у секции.
- На тёмной карточке форма заявки стоит без своей плашки (не «форма в форме»).
- Заголовок секции по центру без метки — опция `center` у `Section.astro`
  (модификатор `.section-head--center`).

### Что ещё не сделано

- **Доставка заявок.** Форма шлёт событие `lead:submit` с готовым объектом заявки — подключить
  Telegram + Google Таблицу через Apps Script (скилл `lead-forms-telegram`).
- Поиск машин: «шкода октавиа» первой строкой даёт марку, а не модель.
- Аналоги в `car-extra.json` (232 модели) — наше предложение. Заказчику: вычитать по
  `ВАРИАНТЫ_ПОИСКА.html` (пометка «по аналогии») и лучше завести эти машины в свой xlsx —
  тогда запись из `car-extra.json` убирается (сборка сама скажет, какую).
- Нет в прайсе «озонации» и «предпродажного пакета» — ситуации «запах» и «продажа» ведут на
  то, что есть. Появятся у заказчика — добавить в прайс и в подборки.

## Порядок работ

**1. Дизайн (сейчас).** Чистый фронтенд, быстрые итерации: пользователь смотрит глазами и
говорит точечно, что поправить. Правка → сборка → скриншоты браузером (мобильный и ПК) и сверка → «смотри туда».
Разведки минимум: правка в названный элемент, соседние компоненты не трогаем.

**2. Компоненты и токены.** Когда стилистика устоялась — всё повторяющееся выносится в
компоненты, а цвета, скругления, шрифты, отступы и меры строки — в переменные `:root` в
[akb-bu/src/styles/global.css](akb-bu/src/styles/global.css). Цель: «поменяй акцент» и
«сделай поля шире» — это правка одной строки, а не обход страниц.

**3. Скилл дизайн-системы.** Из устоявшихся токенов и компонентов собирается скилл — ядро
системы. После этого **любая новая страница верстается через него**, а не с нуля.

**4. Функциональная часть.** Подбор услуги и калькулятор: марка → модель → класс (с поиском
по первым буквам — прямое требование заказчика), выбор услуг, подсчёт суммы, заявка.
Человек не должен теряться в 162 позициях. Формы: имя + телефон с маской, чекбокс согласия,
в заявку уходят URL страницы, марка/модель/класс, UTM.

**5. Деплой.** Боевой контур: домен **dssever.ru**, хостинг Reg.ru (тот же аккаунт, что у
noblefarm.ru и park-sever.ru). Push в `main` → GitHub Actions собирает и льёт `dist` по SCP
в каталог домена. Подробности, доступы и порядок действий — в
[DEPLOYMENT.md](DEPLOYMENT.md). Адрес сайта и префикс пути живут в `SITE_URL`/`BASE_PATH`
в [.github/workflows/deploy.yml](.github/workflows/deploy.yml): пути к файлам и внутренние
ссылки идут через [akb-bu/src/lib/paths.js](akb-bu/src/lib/paths.js), абсолютных `/img/…`
и `href="/…"` в компонентах быть не должно. Пока идёт дизайн, сайт закрыт от поисковиков
переменной `SITE_NOINDEX` (мета-тег + `robots.txt`) — снять перед сдачей.

**6. SEO и скорость.** Уникальные title/description, canonical, schema.org
(LocalBusiness / Service / BreadcrumbList / FAQPage), sitemap.xml, robots.txt, редиректы.
Прайс и виджет класса отдаются в готовом HTML — не рисуются скриптом после загрузки.
Прогон PageSpeed после каждого заметного этапа.

**7. Аналитика.** Метрика с целями: отправка формы, клик по телефону, переход в мессенджер,
использование виджета класса. Вебвизор.

## Как работать

- Каждый шаг — ради заявки. Блок, который не ведёт к «оставить телефон» или к доверию, не нужен.
- Дизайн-решения и отвергнутое — в памяти проекта (`detailing-design-decisions`). Отвергнутое
  повторно не предлагать.
- **Категории сайта строим от прайса, а не от ТЗ** (решено 22.09.2026). Шесть плиток —
  «Мойка и уход», «Химчистка», «Полировка и кузов», «Защитные покрытия», «Плёнки и стёкла»,
  «Перетяжка и пошив» — разбирают все 27 листов и 162 услуги без остатка. Семёрку категорий
  из ТЗ (с «Малярными работами» и «Дооснащением», которых в прайсе нет) не восстанавливать;
  появятся цены от заказчика — добавим плитки тогда. Границы категорий живут в `content.json`,
  состав и цены считаются из `prices.json` в `lib/catalog.js`.
- Дев-сервер: `npx astro dev --background --host 127.0.0.1 --port 4321`. HMR scoped-стилей
  `.astro`-компонентов на этом пути не работает — после правки компонента сервер
  перезапускать (`astro dev stop` → старт).
- Проверка на экране пользователя: Windows-масштаб 150%, монитор 1920 → **~1280 CSS-px**.
  Значения `max-width` выше этого он физически не увидит.
- Общие правила вёрстки (сетка на токенах, контраст текста, одна плотность наборного текста,
  мера строки в `ch`, списки без разделительных линий) — в глобальном `~/.claude/CLAUDE.md`,
  здесь не дублируются.

## Инфраструктура: что закладываем сейчас

Дешевле поставить до 39 страниц, чем чинить после.

- [ ] `services.json` — карта URL из ТЗ и привязка к прайсу. Из неё же строятся мега-меню,
      хлебные крошки, блок «смежные услуги» и sitemap. Без неё 39 страниц разъедутся.
- [ ] `npm run prices` — обёртка над импортёром + проверка: нет строк «не для сайта», все
      разделы из `services.json` нашлись, число услуг не упало относительно прошлого прогона.
      Падает — сборка не идёт.
- [ ] `Layout.astro` принимает SEO-props (title, description, canonical, og, noindex) и
      печатает schema.org. Одна точка на весь сайт.
- [ ] `@astrojs/sitemap` + robots.txt сразу, а не «потом перед сдачей».
- [ ] Компонент формы — один, на все точки входа (модалка, блок в теле, перед футером),
      заголовок и текст кнопки — props. Отправка пока заглушка.
- [ ] `track(event)` — единая обёртка над целями Метрики, чтобы не искать вызовы по вёрстке.
- [x] GitHub Actions: сборка и выкладка на Reg.ru (dssever.ru) по push в `main`.
- [x] Автотест поиска перед сборкой (`npm run test:search`) — машины, услуги, ситуации.
- [x] Пути через `paths.js` — сайт одинаково работает и в подпапке, и в корне домена.
